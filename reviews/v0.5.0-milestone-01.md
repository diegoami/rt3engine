**1. The loader parses all three saves.** `rt3ctl save inspect --path <file> --json` succeeded on all three fixtures and returned a complete inventory (terrain, tiles, cities, buildings, companies, players, events) with no error. `crates/rt3-kit/src/save.rs:54-78` requires every proven section: `GmpMap::peek_version(bytes) == Some(9701)`, then the source-map field, framed terrain, tiles, cities, buildings, companies, players and events — any missing section returns `None`.

**2. **3. The SHA-256 implementation is correct.** `crates/rt3-kit/src/save.rs:81-153` is a hand-written SHA-256. ## Notes for the implementer

- The `save diff` JSON reports a `capacity` for the `tiles` section, but `rt3_kit::tiles::TileSections` has no capacity concept — `crates/rt3ctl/src/save_diff.rs:211-224` synthesises it as `records.len()`, a tile-record count, while the same JSON key means *slot* capacity for the sparse and fixed collections. For the controlled pair both readings give the same `0`, so no committed number is wrong; I am recording this as an observation, not a finding, because no claim depends on it and fixing it would change a committed artifact.
- `crates/rt3ctl/src/save_cmd.rs:83` calls `companies::founded_year(record).unwrap()`. With the committed constants this cannot panic (`COMPANY_BLOB_BYTES = 30_340` and `COMPANY_FOUNDED_YEAR_OFFSET = 67`, and `fixed::parse_candidate` rejects any header whose record size is not exactly `COMPANY_BLOB_BYTES`), so I do not raise it as a finding. It becomes a panic only if the two constants are ever desynchronised — I reproduced that by moving the offset past the record, and the panic surfaced in `save_cmd.rs:83` rather than as a clean error. Worth a `?` when the collection format is next touched.
